A 24.7-minute detailed troubleshooting session by Stefan Catargiu (BIMvoice) diagnosing why an Information Delivery Specification (IDS) rule created in usBIM / IDS Editor failed to validate wall types in Bonsai, returning "Not Available" / zero matching elements. `promotional_ratio: medium` (recurring references to BIMvoice community and bootcamp).

## 1. The Applicability Filter trap in IDS authoring
- A community member attempted to write an IDS rule checking that all walls with "STRUCTURE" in their name have `LoadBearing = True`. The IDS check repeatedly returned `0 of 0` matching elements.
- Stefan identifies the root cause in the IDS facet definition:
  1. The user set the applicability filter to IFC Class = `IfcWall` (the instance occurrence).
  2. However, the naming convention was defined at the type level (`IfcWallType`). In IFC, an instance `IfcWall`'s name attribute is usually an instance identifier, while the thickness and construction name live on `IfcWallType.Name`.
  3. Because the applicability facet targeted the occurrence class while querying type attributes, the filter matched zero elements.
- **The rule**: If auditing type naming conventions, the IDS facet MUST target the type class (`IfcWallType`), not the physical occurrence (`IfcWall`).

> **→ Answers Open Problem 12 (Validation / IDS rules).** Clarifies how buildingSMART IDS schema facets bind to IFC data structures.

## 2. Property Set location: Type vs. Occurrence inheritance
- Stefan demonstrates adding `Pset_WallCommon.LoadBearing = True` to satisfy the IDS requirement.
- In his initial attempt, Stefan adds the property set to the physical wall instance (`IfcWall`). The IDS audit **still fails**.
- Why? Because the IDS rule specified that the *Type* must carry the property. In IFC, property sets can be associated with an occurrence or with a type object. When an IDS specifies a requirement on `IfcWallType`, the property set must be assigned directly to the type definition (`Selected IfcWallType → Pset_WallCommon`), not to the occurrence in the building storey.
- Stefan notes that IDS audits evaluate the project's type library definitions directly, even though type objects are invisible in the 3D viewport.

> **→ Directly corroborates [[_Sources/YT_sdNStKd-fqE_bimvoice_bonsai_vanishing_geometry_type_vs_element|sdNStKd-fqE]]**: property inheritance in IFC is explicit; attaching metadata to an instance does not satisfy a type-level specification, and vice versa.

## 3. Pattern matching syntax in IDS
- Stefan demonstrates using regular expression patterns in IDS attribute facets (e.g. pattern `.*WALL.*` or `.*STR.*`).
- He cautions against restrictive character sets generated by GUI assistant prompts (e.g. patterns restricting characters to letters only when names contain numbers such as `WALL_300`).
