# Source Note - Ifc Architect: ⚠️⚠️ A DEMOLITION PLAN IS A QUERY - `Pset_*Common.Status` and the Filter That Generates Phase Sheets From One Model (YouTube _hADRIo-ma4)

**BlenderBim-era (2024-02); read because no Bonsai-era replacement exists.** `promotional_ratio: none`.

> ⚠️⚠️ **Date this one hard.** He says phasing is new and moving: *"about a year ago **this was not possible** really, so it is always getting better"*, and of his own method: *"it is my current process for doing this, but **in the future it's most likely going to work a bit better**."* **The IFC field is standard and stable; the workflow around it in 2024 is explicitly provisional.**

## ⚠️⚠️ 1. THE FIELD: `Pset_<Class>Common.Status`, with values `existing` / `demolish` / `new`

> *"Create a **`Pset_WallCommon`** — if we were doing this for a window or a door it would say **`Pset_DoorCommon`**, **`Pset_WindowCommon`** — **that's the logic.** … inside the Pset common there is a **`Status`** element."*

Values used: **`existing`**, **`demolish`**, **`new`**, with *"you can have temporary"* mentioned as a further option.

> **→ ⚠️⚠️ THESE ARE THE SAME THREE PHASES THIS PROJECT ALREADY CARRIES AS DXF LAYERS — existing / demolished / new — AND THERE IS A STANDARD IFC PROPERTY FOR THEM.**
>
> **Our layer taxonomy maps one-to-one onto `Pset_*Common.Status`.** `data/cad/` exports existing/demolished/new layers; the IFC-native equivalent is a **property on the element**, not a layer. **That is strictly better**: a layer is a drawing concept that has to be maintained in parallel with the model, while a status property is model data that every view can query. **Directly actionable, and it needs no Bonsai** — `IfcOpenShell` can write a property set.
>
> ⚠️ **He notes the naming pattern is not universal**: *"although it does break eventually."* See §5.

## ⚠️⚠️ 2. A DEMOLITION PLAN IS A FILTER OVER ONE MODEL

The payoff, and the most actionable finding in this round for our own sheet set:

> *"Inside of it you can see there are **include and exclude filters**… you can use a **formula** to say **exclude everything that has a new status**… `IfcElement` … `/Pset_.*Common/.Status = "new"` … and when you activate it, **everything that is new is now hidden**. So now we can say create drawing, and **we've got essentially a DEMOLITION PLAN which shows the existing and what will be demolished** — and then here is our previous drawing which had all the new elements in it as well."*

> **→ ⚠️⚠️ ONE MODEL, MANY PHASE SHEETS, GENERATED BY A DECLARATIVE QUERY STORED ON EACH DRAWING.**
>
> **This is the same mechanism as the CSS attribute selector found in [[_Sources/YT_HEb7fWJduXg_ifcarchitect_page_layout|HEb7fWJduXg]] §4** (`.IfcGeographicElement[name="site"]`), now with a regex over property-set names and a value test — **so the filter language reaches into property sets, not just classes and attributes.**
>
> **And it is the right implementation of a convention this vault already holds.** [[18_Digital_Toolchain/analysis/Drawing_Conventions_From_Practice|Drawing Conventions From Practice]] §3 records *a services sheet has two audiences and therefore two configurations*, observed as **layer toggles**. **A query beats a layer on every axis**: it reads the model's own data rather than a parallel taxonomy, it is text that can be committed and diffed, and **a sheet's content becomes a stated rule rather than a remembered click.**
>
> **→ Route as the design our own generator should use for the phase sheets**, whether or not Bonsai is ever involved. ⚠️ **And note the failure mode: a selector with a typo excludes nothing and reports nothing** — so the gate is *assert the filter matched something*, the same shape as the vocabulary checks elsewhere in this round.

## ⚠️⚠️ 3. THE CRITICISM: he puts phase on the TYPE, which multiplies the type library

His stated three-step recipe, drawn on screen:

1. **a unique TYPE per phase** — `wall 100 existing`, `wall 100 demo`, `wall 100 new`;
2. **a unique PROPERTY SET** carrying the status;
3. **a unique MATERIAL**, so the phase prints distinguishably.

Changing an element's phase means **reassigning its type**: *"click on this little pencil icon and change it from… `w 100 existing` to `w 100 demo`."*

> **→ ⚠️⚠️ PHASE IS NOT A PROPERTY OF WHAT KIND OF WALL SOMETHING IS. IT IS A PROPERTY OF THIS PARTICULAR WALL.** Putting it on the type forces **one type per (construction × phase)** — and since [[_Sources/YT_jTL3a6QwckA_ifcarchitect_custom_wall_type|jTL3a6QwckA]] §2 establishes that **thickness is also a type property**, the library grows as the **product** of thicknesses and phases. For this flat that would be every wall construction × three.
>
> ⚠️ **He half-admits it** — *"it is my current process… in the future it's most likely going to work a bit better"* — and his reason is mechanical, not conceptual: **he wants new instances to inherit the property automatically**, which is what types give you.
>
> **→ ADOPT THE FIELD, NOT THE PATTERN.** Set `Status` **per instance**. We author programmatically, so "inherit automatically" costs us nothing — **it is a column in a CSV.** **This is the clearest case in the batch where a GUI-driven workaround should not be copied into a generated pipeline.**

## ⚠️ 4. A model-wide status filter, including SELECTION

Beyond drawings, `costing and scheduling → enable status filter` gives **visibility** and **selection** toggles per status: hide everything demolished; **select everything new.**

> **→ ⚠️ SELECTION BY PHASE IS THE INTERESTING HALF, AND IT IS A COSTING CAPABILITY, NOT A DRAWING ONE.** The gap analysis's cost design calls for **staged commitment** — *"price by trade stage… do not commit Stage 4 rates during Stage 1."* **Phase-filtered selection is the mechanism that makes phase-filtered quantities possible.** ⚠️ Not demonstrated for quantities here; recorded as the obvious adjacency.

## ⚠️⚠️ 5. The pattern BREAKS for spaces — and the fallback is vendor-specific and half-supported

> *"There's a **`Pset_SpaceCommon`** — unfortunately **we're not going to use this because it DOESN'T HAVE A STATUS ELEMENT** inside of it, don't know why… we are going to create something different which is an **`EPset_status`**, which is **kind of unique to BlenderBim** — I think it does align with the IFC standard, **but I don't think it exists elsewhere**."*

And it only half works: *"there's a reason I haven't used this for these others, because **it doesn't show up in 2D**"* — the exclude filter does not act on it either, and the space remains in the drawing (harmlessly, because spaces are transparent).

> **→ ⚠️⚠️ A VENDOR-SPECIFIC PROPERTY SET USED AS A FALLBACK WHERE THE STANDARD FALLS SHORT, WITH PARTIAL TOOL SUPPORT AND ACKNOWLEDGED PORTABILITY DOUBT.**
>
> **This is the SECOND instance in this round of the same reflex** — the first being the **Blender-specific quantity set** preferred over `IFC4 base quantities` in [[_Sources/YT_VgvPk78IU0U_ifcarchitect_bonsai_2d_drafting|VgvPk78IU0U]] §13, *"because it works a little bit better right now."*
>
> **⚠️ For a project whose entire premise is that the IFC is the portable master, that is the pattern to watch for.** Both times the vendor extension was chosen for short-term convenience, and both times the presenter was unsure what it costs downstream. **→ A standing rule for any adoption here: prefer the standard property set; if a vendor extension is used, record why and what breaks without it.**

## Conventions and mechanics

6. **⚠️ His phase colour convention, stated as personal practice**: *"the **existing** normally I would give it a **grey** material, the **demolish** I would give it a **blue or a light grey**, and the **new** I would give it a **red or pink**."* ⚠️ **Offered *"completely metaphorically"* as a demonstration, and this presenter's conventions are South African** — see [[_Sources/YT_dPWQbjaeoyo_ifcarchitect_lineweights_css|dPWQbjaeoyo]] §6. **Recorded as one practitioner's convention, not as a standard**, and ⚠️ **it differs from common European practice, where demolished is often dashed and new is solid.** Not routed as a rule.
7. **The material name is the CSS class — fourth confirmation.** He points the camera at a `phases.css` stylesheet and renames the three types' material layer sets to `existing`, `demo`, `new`; the sheet then prints grey / blue / red. **→ Consistent with [[_Sources/YT_dPWQbjaeoyo_ifcarchitect_lineweights_css|dPWQbjaeoyo]] §1–2.**
8. **⚠️ Another manual-commit gotcha**: *"**always tick to confirm, otherwise it's not going to work.**"* **→ Belongs with the `shift G` / refresh / `create drawing`-before-`create sheets` family** — the list of explicit re-synchronisation steps a headless script would have to make, now four entries long.
9. **`generate spaces from walls`** creates `IfcSpace` objects from selected wall geometry in one command. ⚠️ **Directly relevant**: this project maintains room geometry by hand in `room_rollouts.csv`, and space objects are what `Qto_SpaceBaseQuantities` attaches to.
10. **A spatial-hierarchy gotcha he hits live**: an object created outside the active collection lands outside `project → site → building → storey` and must be reassigned via `spatial container`. *"When you create an object, make sure you're in the collection when you create it."*
11. **Phasing applies to furniture too** — `Pset_FurnitureTypeCommon` on a furniture type, set to `new`.
12. **The three-black-lines problem**: before materials are assigned, all three phases *"look exactly the same in 2D **even though the model knows that they're different things**."* **→ A crisp statement of the split between model semantics and drawing appearance** — the data is right and the sheet is useless until styling connects them.
13. **Drawing setup repeated**: plan on `my story` not origin, extent 5 m, **scale 1:50** *"because it looks a bit better."* ⚠️ Fourth storey-not-origin confirmation, and a third different scale choice from the same presenter across four videos — **consistent with the reading that scale is per-sheet judgement, not a standard.**
